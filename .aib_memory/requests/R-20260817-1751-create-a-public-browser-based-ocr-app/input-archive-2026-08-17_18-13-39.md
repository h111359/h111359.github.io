## Input

### Goal

Create a public browser-based OCR app that extracts editable text from a user-provided image. The app must recognize English, Bulgarian, and Greek while keeping the selected image inside the browser.

### Users and value

- Primary users are public site visitors who need to extract text from images of documents or notes.
- The app fills a gap in the current Projects catalog, which has no image OCR utility.
- The feature is requested for the current implementation iteration.
- Existing project applications and their behavior must remain available.

### Scope

- Create a dedicated OCR application at `apps/image-ocr/index.html`.
- Add the application as the fourth project card on `apps.html`.
- Update the Projects page title copy, project count, description, Open Graph description, and footer text to reflect four applications.
- Process one image at a time.
- Accept images through a file picker, drag-and-drop, or clipboard paste.
- Accept any image format the current browser can natively decode.
- Do not impose an application-defined file-size limit.
- Display a preview of the selected image.
- Allow rotation in 90-degree increments and resetting the image to its original orientation.
- Run OCR against the currently displayed orientation.
- Support English, Bulgarian, and Greek recognition.
- Let users select one or more OCR languages.
- Select English by default and provide an easy way to select all three languages.
- Display OCR loading and processing status so users can tell that work is in progress.
- Present recognized text in an editable plain-text field.
- Provide controls to copy the result and download it as a UTF-8 `.txt` file.
- Allow a new image to replace the current image and reset obsolete results and errors.

### OCR and privacy requirements

- Use Tesseract.js for browser-local OCR.
- Load a pinned compatible Tesseract.js runtime, worker assets, and required language data from a public CDN.
- The selected image and recognized text must not be uploaded to an application server or external OCR service.
- Network requests for OCR runtime and language assets are permitted.
- Explain briefly in the interface that image processing happens locally in the browser.
- Use the Tesseract language identifiers `eng`, `bul`, and `ell` for English, Bulgarian, and Greek.
- Load only the language data needed for the current selection.

### Input and validation behavior

- Use browser-native image decoding instead of a hard-coded format allowlist.
- Reject files or clipboard content that cannot be decoded as an image.
- If clipboard data contains no image, retain the current state and show a clear message.
- Do not reject an image solely because of its file size.
- If a large image exceeds available browser memory or cannot be processed, show a recoverable error rather than leaving the interface stuck.
- Prevent OCR from starting until an image and at least one language are selected.
- Prevent overlapping OCR operations caused by repeated activation of the recognition control.

### Result behavior

- Preserve Unicode characters in English, Bulgarian, and Greek throughout display, editing, copying, and downloading.
- Copy the current edited value rather than the original unedited OCR response.
- Download the current edited value as UTF-8 plain text.
- Derive a sensible `.txt` filename from the source filename when one is available.
- Give visible success or failure feedback after a copy attempt.
- Keep the result editable after recognition completes.
- Clear or mark a previous result as obsolete when the source image or its rotation changes.

### Interface requirements

- Use English for all labels, instructions, progress messages, validation messages, and errors.
- Provide clear controls for selecting an image, choosing languages, rotating and resetting the preview, starting OCR, copying text, downloading text, and starting over.
- Support keyboard operation and visible keyboard focus.
- Associate instructions, controls, progress updates, errors, and the result field with appropriate semantic HTML and accessible labels.
- Announce important processing and error-state changes to assistive technologies without moving focus unexpectedly.
- Reflow without horizontal page scrolling at 320 CSS pixels.
- Remain usable on current evergreen desktop and mobile browsers.
- Preserve essential instructions and controls when animation is disabled.
- Follow the visual language of the existing portfolio where practical while allowing the standalone utility to have app-specific styles.

### Error and recovery requirements

- Handle image decode failures, OCR runtime loading failures, language-data loading failures, OCR failures, clipboard permission failures, and copy failures.
- Show errors in plain language and retain enough state for the user to retry.
- Restore enabled controls after a failed operation.
- Do not replace the entire document body when reporting an error.
- A failed OCR attempt must not require a full page reload before retrying.
- If the browser does not support a preferred input method, other available image-selection methods must remain usable.

### Out of scope

- Multiple-image or batch OCR.
- PDF input or PDF-to-image conversion.
- Automatic language detection.
- Server-side processing or external OCR APIs.
- A fully offline installation or repository-vendored OCR language datasets.
- Direct camera-capture controls beyond behavior provided automatically by the browser’s file picker.
- Cropping, deskewing, brightness, contrast, grayscale, or other advanced preprocessing controls.
- Preservation of the source document’s visual layout.
- hOCR, searchable PDF, word-processing, or structured-data export.
- Translation, spell-checking, and automatic correction of recognized text.
- A numeric OCR accuracy guarantee.
- Changes to the three existing project applications.

### Constraints and assumptions

- The solution must remain compatible with GitHub Pages static hosting.
- No server-side code, build system, transpiler, package manager, or secret API credential may be introduced.
- JavaScript must run directly in the browser.
- An internet connection is required when uncached CDN runtime or language assets need to be downloaded.
- Browser-native format support varies; a format is supported only when the active browser can decode it.
- Very large images may fail because of device memory limits even though the app imposes no explicit size limit.
- Representative inputs are expected to contain clear printed or digitally rendered text.
- Handwriting, stylized lettering, low-resolution text, severe distortion, and poor contrast may reduce recognition quality.
- OCR quality may vary by image and language; successful recognition does not mean perfect transcription.
- Adding the OCR card changes the Projects page from three to four listed applications.

### Acceptance criteria

- Opening `apps/image-ocr/index.html` displays a functional English-language OCR interface.
- `apps.html` displays four project cards and contains an accurate OCR card linking to the new application.
- Project-page descriptions, project counts, and relevant metadata consistently describe four applications.
- A user can select one image through the file picker, drag-and-drop, or clipboard paste.
- The app attempts any browser-decodable image without applying an explicit application-level file-size cap.
- A user can select English, Bulgarian, Greek, or any combination of those languages, with English selected initially.
- Clear representative images containing English, Bulgarian, and Greek text each produce recognizable text in their respective language modes.
- No numeric recognition-accuracy threshold is required.
- The selected image is processed locally and is not transmitted to an OCR service.
- The preview can be rotated in 90-degree increments and restored to its original orientation.
- OCR uses the current preview orientation.
- Processing progress or status remains visible until recognition succeeds or fails.
- Recognized text can be edited, copied, and downloaded as a UTF-8 `.txt` file without corrupting Bulgarian or Greek characters.
- Invalid input and runtime, language-loading, clipboard, copy, memory, and OCR failures produce understandable recoverable messages.
- The interface is keyboard-operable, has visible focus, and reflows at 320 CSS pixels without horizontal page scrolling.
- Existing project cards and applications continue to work after the new card is added.
